## 1. 목표와 배경

**만들 것:** 참여자가 챗봇 면담을 마친 뒤, 규칙이 만든 형상 후보 가운데 하나를 고르고 정해진 항목 안에서 고친 다음, VR에서 그 형상을 직접 배치하거나 보기만 하는 실험의 프로토타입.

**왜 이렇게 바뀌었나:** 지금 렌더는 도형 위주라서, 참여자가 화분·인형처럼 구체적인 것을 말하면 아무것도 그려지지 않습니다. 형상이 자기 것으로 받아들여지지 않으면 RQ V4의 구별감 측정이 의미를 잃습니다. 생성 모델을 실행 중에 쓰는 대신, (가) 문헌에서 되풀이해 나오는 형태로 기본 형상 목록을 넓히고 (나) 참여자가 후보를 고르고 고치게 해서 차이를 메우기로 했습니다.

**일정:** 한국HCI학회 12/2 투고. 그 전에는 참여자 없이 팀 내부 시행만 가능할 수 있습니다. 그래서 에셋을 많이 만드는 것보다 **면담부터 사전 측정까지의 흐름이 끝까지 도는 것**이 먼저입니다.

## 3. 이미 확인한 사실 (다시 조사하지 않음)

- **사전에 없는 명사는 기록 없이 사라집니다.** v1 매퍼에 "가슴 앞에 작은 화분이 있어요. 초록색이에요."를 넣으면 색과 신체 위치만 나오고, 화분은 `_unmapped`에도 없습니다. 물병·인형도 같습니다. 사물 낱말은 `shared/lexicon/layer1_lexicon.v0.json`에 33개뿐입니다. 같은 문장에서 "작은"도 크기 슬롯에 들어가지 않았는데 원인은 확인하지 않았습니다.
- **구름이 구름처럼 안 보이는 원인(코드 기준):** 기본 밝기 0.7(`SceneParams.cs`)과 하늘 지평선 0.74(`EnvironmentBuilder.cs:29`)가 거의 같고, mist는 밀도 0.5가 곱해지며, `SceneSpecFade.shader`가 가장자리 알파를 0으로 만들어 윤곽을 지우고, 구 하나를 노이즈로 미는 구조라 작은 덩어리가 생기지 않습니다. 제안된 수정은 작은 구 여러 개를 고정 배치해 합친 메시와 윤곽을 살리는 셰이더입니다. 헤드셋에서 구름으로 읽히는지는 확인되지 않았습니다.
- **형태 변형 mist→blob은 윤곽과 함께 유효 불투명도도 0.5→1로 바꿉니다**(`OwnershipVariantGenerator.cs`의 형태별 밀도 표). mist 밀도를 바꾸면 색 차이 계산(`ColorMetrics.cs`)도 같이 맞춰야 합니다.
- **Unity(`main` 기준):** 기본 렌더 파이프라인, 선형 색 공간, 매니페스트에 XR·렌더 파이프라인 패키지 없음. 로더는 파일을 직접 읽습니다(`File.ReadAllText`). `BatchCapture`는 에디터 전용입니다.
- **문헌:** IFS part의 형태를 분류하거나 빈도를 센 연구는 찾지 못했습니다. 고정 도구(SelVReflect, 20명 중 8명이 표현 방법을 몰라 함)와 생성 도구(Refugio, MentalImager, Memory Printer) 모두 불일치를 보고했습니다. 상세는 `reports/IFS part 심상 범주 조사.md`.
- **인용하면 안 되는 것:** Sweezy(2011) "쇠로 된 손 → 여덟 살 남자아이"(출처 미확인), Emotion Carrier를 심상 범주의 근거로 쓰는 것(텍스트 주석 개념). Shigyo 외(2024, ACM MM)의 3D 모델 제작 주체는 원문 미확인.
- **Codex 독립 검토 D2는 실행되지 않았습니다.** 프롬프트는 `docs/codex-reviews/prompts/D2_prompt.md`에 있습니다. 로컬에서 인증이 되면 한 번 돌려 `docs/codex-reviews/D2.md`에 저장하고, G1–G6과 어긋나는 지적이 있으면 판정을 기록합니다.

## 4. 작업 단계

### 단계 A. 조사: 사람들은 내적 경험을 무엇으로 나타내는가

지난 조사의 질문은 "IFS가 범주를 정했는가"였습니다. 이번에는 **형태 목록**을 모읍니다.

- 범위
  - 감정·내적 상태를 그리거나 만들게 한 연구(그림, 점토, VR 제작)
  - 모래상자·피규어 선택 연구(어떤 미니어처가 선택되는가)
  - 증상·감정 심상 면담 연구(통증, 불안, 우울에서 보고된 사물 은유)
  - 감정 은유 연구(언어학에서 정리한 은유의 원천: 그릇 속 액체, 불, 무게, 어둠 등)
  - 한국어 자료(한국어 화자의 감정 은유와 심상 표현)
- 기존 노트(`research_notes/IFS part 심상 범주 조사/`)에 이미 있는 문헌은 다시 찾지 말고 그 위에 쌓습니다.
- 주장마다 확인 수준(원문 확인 / 초록만 확인 / 2차 인용 / 서지만 확인)을 적고, 열지 않은 문헌을 근거로 쓰지 않습니다.
- 산출물: `reports/심상 외재화 형태 목록 조사.md`. 연구별 형태 목록과, 그것을 묶은 범주 표(범주, 대표 예, 나온 연구 수, 확인 수준)를 담습니다. 조사 노트는 `research_notes/` 아래 새 폴더에 둡니다.
- 이 조사가 줄 수 있는 것은 우선순위이고 빈도가 아닙니다. 과제가 다른 연구의 비율을 part 심상의 비율처럼 쓰지 않습니다.

### 단계 B. 에셋 제작 계획

`docs/asset-plan.md`를 씁니다.

- **범주와 기본 형상 표:** 범주, 기본 형상 이름, 근거 문헌과 확인 수준, 이 형상으로 가는 한국어 낱말 목록(사전 항목 초안), 제작 방법, 우선순위.
- **형상 사양:** 세부가 적고 색·질감이 없는 중립 모형. 크기 기준은 기존 모양 모형과 같게 맞춥니다(`docs/shape-mapping.md`). 말한 속성(색, 밝기, 투명도, 질감, 크기, 움직임)을 그 위에 입힐 수 있어야 합니다.
- **묶음 단위로 시작합니다.** 화분·그릇·병을 낱말마다 만들지 않고 "담는 것" 하나처럼 묶습니다.
- **제작 방법은 형상마다 하나를 고릅니다:** 코드로 만드는 절차 모형 / 라이선스가 맞는 공개 모형(출처와 라이선스 기록) / 생성 모델을 제작 도구로 써서 고정(모델 digest와 결과 해시 기록, 로컬 실행).
- **넣지 않을 것의 기준:** 아이 형상, 공격하는 존재처럼 연구 범위(추방자 제외, 치료 표현 금지)와 부딪히는 형태. 문헌에 자주 나와도 뺀 것은 뺀 이유와 함께 표에 남깁니다.
- **12/2 전 제작 수:** 일정 안에 만들 수 있는 첫 묶음과 그 뒤로 미룰 것을 나눕니다.
- 이 계획은 연구 책임자의 승인이 필요합니다. 계획을 쓰고 요약을 보고한 뒤, 승인을 기다리는 동안 에셋 목록과 무관한 단계 D의 D1–D4를 먼저 진행합니다.

### 단계 D. 구현

순서는 흐름이 먼저 끝까지 도는 쪽으로 잡았습니다.

- **D1. 사전에 없는 명사 기록.** 확정 텍스트의 명사 가운데 사전에 없는 것을 `_unmapped`에 남깁니다. 규칙은 결정적이어야 합니다. 위 "작은 화분"에서 크기가 빠진 원인도 함께 확인합니다.
- **D2. 형상이 보이지 않게 되는 매퍼 오류 수정.** "거의 투명"이 0이 되는 것, 거리 0, 자세가 참여자 자신의 것인지 part의 것인지 구분.
- **D3. 후보 생성기.** spec 하나에서 후보 여러 개를 만듭니다(G8, G9). 같은 입력은 같은 후보를 냅니다. 비어 있는 자리가 없어 후보가 같아지는 경우의 처리 규칙을 정합니다. `OwnershipVariantGenerator`의 결정적 변형 방식을 참고할 수 있습니다.
- **D4. WebGL 미리보기 시험 빌드.** 예시 씬을 WebGL로 빌드해 로더가 JSON 문자열을 받게 하고, held-out spec에서 데스크톱 캡처와 평균 색·덮인 화소 수를 비교합니다. 빌드가 안 되거나 차이가 크면 원인을 기록하고, 대안(Unity가 뒤에서 캡처한 이미지를 웹에 표시)으로 갈지 판정합니다. 외부 CDN을 쓰지 않고 챗봇 서버가 로컬에서 내보냅니다.
- **D5. 후보·조절 화면과 API.** 후보 요청, 선택, "맞는 것이 없다", 조절값 저장. 조절 패널은 G10의 항목만 둡니다.
- **D6. 기본 형상 경로.** 낱말 → 범주 → 기본 형상을 사전으로 잇고, 승인된 첫 묶음 에셋을 넣습니다.
- **D7. 구름 수정.** 3절의 진단을 렌더 시트와 대조한 뒤 수정합니다. 밀도를 바꾸면 색 차이 계산과 관련 테스트를 함께 고칩니다.
- **D8. V4 러너 연결.** 고르고 고친 spec을 배치/보기만 러너가 읽게 하고, 사전·사후 측정 화면에 두 평정 문항을 넣습니다.
- **D9. 기록.** 흐름 표 9단계의 항목을 세션 기록에 남깁니다. 참여자 데이터는 git에 올리지 않습니다.
- **D10. 내부 시행 준비.** 팀원이 1–6단계를 해 볼 수 있는 실행 방법과 점검표를 씁니다. 볼 것은 "맞는 것이 없다" 비율, 대표성 점수, 어떤 심상에서 막혔는지입니다.

## 5. 설계가 갈리는 결정

CLAUDE.md의 절차대로 Claude 하위 에이전트와 Codex에게 따로 안을 받아 판정합니다.

- 후보를 어디서 무엇으로 만들지(Python / Unity, 변형된 spec / 덮어쓰기 목록)와 출처 표시 방식
- 후보 규칙: 어느 자리를 몇 개로 벌릴지, 낱말 해석이 갈리는 자리의 범위
- 기본 형상을 spec에서 어떻게 표현할지(`form.type` 확장 / 별도 필드)와 스키마 영향

## 6. 사람이 정할 것

아래는 정하지 말고, 적어 둔 임시값으로 진행한 뒤 보고서에 "⚠ 사람이 정할 것"으로 표시해 주세요.

| --- | --- |

| 형상을 소개하는 안내 문구 | 초안: "당신이 말한 것을 바탕으로 만든, 그것을 대신하는 형상입니다" |

## 7. 완료 기준

- 합성 대사 시나리오로 1–6단계가 끝까지 돕니다(면담 → 추출 → 후보 → 선택 → 조절 → 사전 측정 화면).
- 같은 확정 텍스트는 같은 spec과 같은 후보를 냅니다(테스트로 고정).
- 사전에 없는 명사가 `_unmapped`에 남습니다(테스트로 고정).
- Python 테스트와 Unity EditMode 테스트가 통과합니다. 통과하지 못한 것은 출력과 함께 보고합니다.
- WebGL 시험 빌드의 결과(성공 여부, 데스크톱과의 차이 수치)가 문서에 있습니다.
- 조사 보고서, 에셋 계획, 갱신된 설계 문서, 결정 기록이 저장소에 있습니다.
- 마지막 보고에는 한 것, 하지 못한 것, 확인하지 못한 것(헤드셋 실기 등), 사람이 정할 것을 나눠 적습니다. 하지 않은 단계를 한 것처럼 적지 않습니다.
