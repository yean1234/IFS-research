## 확인한 사실

1. 지금 색은 웹 조절 화면 첫 항목에서 **정해진 견본 단추**를 눌러 바꿉니다. 값은 값 표의 견본 목록이며, 서버는 견본을 HSL 값으로 돌려줍니다. 따라서 연속된 색 전체를 고르는 기능은 없습니다. 스펙과 덮어쓰기 값은 `material.color: {h,s,l}` 및 `material.color.h/s/l`이고, `h`는 0–1로 표현합니다. (`chatbot/ifs_chatbot/web/stage.js:714-732`, `chatbot/ifs_chatbot/selection.py:1126`, `shared/lexicon/candidate_values.v3.json:411-420`, `shared/schemas/scene-spec.v2.4.json:236-253`, `shared/schemas/selection.v0.5.json:40-42`)
2. 슬롯별 출처는 선택 파일의 `sources`와 `sourceDetails`에 적습니다. 색을 조절하면 `edited`, 건드리지 않으면 기존의 `said`·`default`·`llm_quoted` 등을 유지합니다. `adjustments.items.color`에는 처음·마지막 값과 조작 횟수가 있고, 이벤트에는 조작 시각을 기록합니다. `colorChanged`는 처음과 마지막 HSL이 다른지 나타냅니다. (`docs/decisions.md:352,405`, `chatbot/ifs_chatbot/selection.py:1156-1167,1196-1198`, `shared/schemas/selection.v0.5.json:2665-2767,3087-3089`)
3. 밝기(`material.brightness`)와 투명도(`material.opacity`)는 색과 별도 슬롯입니다. 다만 색 HSL의 `l`도 색의 밝기 성분입니다. 렌더러 밝기와 HSL 명도를 같은 조작으로 취급하지 않아야 합니다. (`shared/schemas/scene-spec.v2.4.json:236-261`, `docs/decisions.md:359`)
4. 뼈대와 결정은 **후보에서 색을 제안하지 않고, 참여자가 조절 화면에서 고르게** 합니다. G17은 후보의 hue 변형을 금지하고, G31은 조절 화면의 색 항목과 변경 기록을 승인했습니다. 이는 직접 조절을 막지 않습니다. (`docs/design-backbone.md:진행 순서·조절 항목`, `docs/decisions.md:354,393-405`) 화면 고정 문구는 초안이며, 바꾸면 출처·상태를 적고 프로토콜 판을 올려야 합니다. (`shared/protocol/selection_protocol.v0.10.json:6`, `AGENTS.md:7`, `docs/participant-protection.md:모든 문구 초안`)

## 권하는 안 하나

**웹 조절 화면에 hue 원형 선택기와 채도 반경을 둡니다.** 색 이름이나 예시 대신 색 면과 키보드 접근 가능한 수치 조작을 제공하고, 화면 읽기 보조에는 색상각·채도 수치를 읽게 합니다. 선택 시 HSL의 `h,s`만 바꾸고 `l`, `material.brightness`, `material.opacity`는 보존합니다. HSL 명도 `l`은 현재 조절 항목 목록에 독립 조작으로 없으므로, 이번 단계에서 추가하지 않습니다. 이렇게 하면 색상 선택과 밝기·투명도 조작이 겹치지 않습니다.

말한 색이 있으면 매퍼가 만든 색을 첫 위치로 표시하고, 참여자가 선택할 때만 바꿉니다. 색을 말하지 않았으면 지금의 중립 기본색을 유지하고 선택기 상태를 **미선택**으로 표시합니다. 중립 기본색을 참여자의 선택으로 기록하지 않습니다. 초기값이 없는 경우도 기본색과 구별해 `initial: null`로 남깁니다.

최소 1단계는 선택 결과를 기존 HSL 덮어쓰기에 연결하고 선택기 버전, 최초·최종 HSL, 조작 횟수와 시각, 슬롯 출처를 기록하는 것입니다. `selection.v0.6`에 선택기 메타데이터를 추가하고, 프로토콜 문구도 새 판에 넣습니다. 새 문구 초안: **“색은 여기에서 고르거나, 지금 색을 그대로 둘 수 있어요.”** Unity는 기존 HSL 키를 계속 읽되 새 선택 판을 명시적으로 받아들이도록 확인하고, 변경된 러너로 헤드셋 빌드를 다시 만듭니다. 새 렌더링 형식이 없어도 판 지원 변경을 검증하는 빌드는 필요합니다.

분석용 색 이름 enum은 원 HSL을 보존한 별도 파생값으로 만듭니다. 무채색 판정과 hue 구간·경계·색 이름 대응표를 자료 보기 전에 고정하고, 기존 기록에도 같은 규칙을 적용합니다. 색 이름 enum만 저장하면 경계 변경이나 재분석이 불가능합니다. 웹 코드·선택 스키마·프로토콜·Unity 파서와 빌드 설정이 변경 대상입니다. 시험에는 선택하지 않음, 말한 색 유지·수정, 기본색에서 선택, 밝기·투명도 독립성, 키보드·화면 읽기, 구버전 선택 파일 호환을 포함합니다.

## 버린 대안

- 헤드셋 안 선택: 참여자는 이미 웹 조절 화면에서 물체를 고치므로 같은 화면에 두는 흐름이 자연스럽습니다. Unity 입력과 빌드 범위도 불필요하게 커집니다.
- 고정 색 견본만 늘리기: 선택 폭은 제한되고 색각 이상 접근성이 약합니다. 채도·명도까지 한 번에 움직이는 2D 면도 별도 밝기 조절과 혼동될 여지가 있어, 이번 단계에서는 hue와 채도 반경만 권합니다.

**위험·불확실성:** 연속 색 선택은 기존 견본보다 참여자 개입과 색상 다양성을 키워 색 관련 결과와 기존 세션의 직접 비교를 어렵게 할 수 있습니다. 색 이름 구간과 무채색 기준은 현재 확인한 HSL 스키마만으로 정할 수 없습니다. 이는 설계 권고이며 해당 기준은 연구팀이 사전 고정해야 합니다.
