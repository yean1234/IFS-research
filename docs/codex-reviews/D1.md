1. **표현과 위치**: Python에서 원본 spec은 그대로 두고, 별도 변형 계획 JSON에 변형값과 기록용 정보를 저장한다.  
   이유: 변형값을 spec에 넣으면 말하지 않은 값에 provenance를 만들어야 하고, 새 필드는 Unity의 엄격한 파서를 통과하지 못한다. 변형 계획은 확정 spec과 구분해 Unity가 파싱한 뒤 `SceneParams`에 적용하고, 형상별 실제 적용값과 기본값 목록을 로그에 함께 남긴다.  
   구체 값: 계획에는 `session_id`, `seed_version`, `trial_id`, `property`, `override_path`, `from`, `to`, `source_status`를 기록한다. seed는 세션 ID와 설정 버전으로 고정한다.  
   근거: [SceneSpecJson.cs:16](unity/Assets/IFS/Runtime/SceneSpec/SceneSpecJson.cs:16), [SceneParams.cs:30](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:30), [SceneParams.cs:50](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:50)

2. **크기**: 원본보다 2배 키우거나 절반으로 줄이고, 방향은 참여자 ID의 고정 해시로 배정해 전체 참여자 간 두 방향을 균형화한다.  
   이유: `layout.size`의 ±0.25가 정확히 ×2/÷2라 규칙이 단순하고 재현 가능하다. 모집 순서에 따라 한 방향이 몰리지 않도록 ID 해시의 홀짝으로 방향을 정하고, 계획 단계에서 각 방향의 수 차이가 1을 넘지 않게 배정 순서를 정한다.  
   구체 값: 원본 유효 size가 `x`면 `x ± 0.25`; 범위를 넘으면 반대 방향을 택한다. 양쪽 모두 불가한 경계값이면 해당 trial은 무효로 기록한다.  
   근거: [SceneParams.cs:165](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:165), [scene-spec.v2.1.json:223](shared/schemas/scene-spec.v2.1.json:223)

3. **색**: 유채색은 hue를 0.25 회전하고 saturation·brightness는 유지한다. 무채색은 hue 0.5, saturation 0.6으로 바꾸고 lightness와 brightness는 유지한다.  
   이유: 유채색 조작은 밝기 차이를 섞지 않고 색상 계열만 바꾼다. 무채색에서는 hue 변경만으로 보이는 차이가 없으므로 채도를 추가하며, 렌더 밝기 슬롯은 두 경우 모두 고정해 색 조작과 밝기 효과를 분리한다.  
   구체 값: 유채색 판정은 유효 saturation `> 0.05`; hue는 `(h + 0.25) mod 1`. 무채색은 유효 saturation `≤ 0.05`; `(h,s)=(0.5,0.6)`으로 설정한다.  
   근거: [SceneParams.cs:80](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:80), [SceneParams.cs:86](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:86), [SceneLoader.cs:666](unity/Assets/IFS/Runtime/Loading/SceneLoader.cs:666)

4. **움직임**: 속도는 고정하고 재생 유형을 바꾼다. 원본이 정지면 Sway로, 움직임이 있으면 다른 재생 묶음 하나로 결정론적으로 교체한다.  
   이유: 속도 변화는 기존 움직임의 정체성을 유지한 채 강도만 바꾸지만, 종류 변경은 연구 질문의 ‘움직임 속성’을 직접 조작한다. 22개 spec 유형이 9개 재생 묶음으로 합쳐지므로, 로그에는 요청 유형과 실제 재생 묶음을 모두 남겨야 한다.  
   구체 값: `still` 또는 기본 still → `swaying`; 그 외에는 실제 묶음 순서 `[Sway,Tremble,Pulse,Drift,Sink,Spin,Expand,Approach]`에서 다음 묶음으로 이동하고 해당 묶음의 정규 유형을 사용한다.  
   근거: [SpecMotion.cs](unity/Assets/IFS/Runtime/SceneSpec/SpecMotion.cs), [SceneParams.cs:93](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:93)

5. **형태**: 원본 렌더 경로 안에서만 대체한다.  
   이유: `form.type` 절차 모형과 `_unmapped` 모양 프리팹은 서로 다른 형상 경로라 경로 간 교체는 두 요소를 동시에 바꾸거나 정보 손실을 만들 수 있다. 같은 경로 안에서 고정 순환시키면 형태만 조작하고 기존 매핑 의미를 보존할 수 있다.  
   구체 값: 기본 `blob`·`blob` → `mist`; `mist→shell`, `shell→fragments`, `fragments→blob`. 모양 프리팹은 `Sphere→Cube→FlatCylinder→Cone→Sphere`. `mist/shell/fragments`와 모양 프리팹이 함께 지정된 비정상 충돌은 무효 trial로 처리한다.  
   근거: [shape-mapping.md:25](docs/shape-mapping.md:25), [shape-mapping.md:29](docs/shape-mapping.md:29), [shape-mapping.md:33](docs/shape-mapping.md:33)

6. **말한 속성 / 기본값 속성 표시**: 변형 대상 속성의 원본 유효값에 대응하는 spec provenance가 있으면 ‘말함’, Unity 기본값에서 왔으면 ‘기본값’으로 기록한다.  
   이유: provenance를 변형본에 복제하거나 새로 부여하면 변형값이 참여자 발화에서 나온 것처럼 보인다. 판정은 렌더링에 실제 쓰인 원본값 기준으로 하며, 변형 사실과 출처 표시는 서로 다른 필드로 관리한다.  
   구체 값: 색은 `color.h/s/l` 중 하나라도 발화 provenance가 있으면 ‘말함’, 모두 미지정이면 ‘기본값’; brightness는 별도 슬롯이므로 이 조작에서는 고정한다. 형태는 `form.type`이 말해졌으면 ‘말함’, 모양 경로는 확정된 shape 낱말의 `_unmapped` 근거가 있으면 ‘말함’; 양쪽 모두 없고 Unity가 blob을 채웠으면 ‘기본값’.  
   근거: [SceneParams.cs:77](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:77), [shape-mapping.md:68](docs/shape-mapping.md:68)

7. **변화 크기 맞추기**: 지각 크기를 수치상 같다고 간주하지 않고, 내부 시행으로 조작을 점검한 뒤 분석에서 조작 종류와 크기를 분리해 다룬다.  
   이유: 색·형태·움직임의 지각 차이를 공통 단위로 맞출 근거가 없으므로 수치를 억지로 일치시키면 오히려 해석이 왜곡된다. 투고까지 약 2주이고 참여자 자료를 모으기 어려운 조건에서는 내부 시행으로 극단값·가시성·중복을 확인하고, 본 분석에서 속성별 효과와 방향을 보고하는 것이 실행 가능하다.  
   구체 값: 내부 시행은 연구팀 전원이 각 trial을 관찰해 조작이 보이는지, 원본과 변형이 동일하게 렌더링되는지 기록한다. RQ1은 속성별 원본 대비 평정 차이와 선택률을 제시하고, 크기 방향과 발화/기본값 출처를 공변량 또는 층화 변수로 포함한다. 지각 크기 보정이 검증되지 않은 한 ‘속성 자체의 우열’로 일반화하지 않는다.  
   근거: [research-design.md:127](docs/research-design.md:127), [research-design.md:152](docs/research-design.md:152)

8. **경계 사례와 처리**:  
   이유: 경계 조건은 실제 변형이 적용되지 않거나 원본과 같은 결과가 되는 상황을 명시적으로 구분해야 한다.  
   구체 값:  
   - size 경계: `x±0.25` 후보 중 범위 `[0,1]` 안의 방향을 사용하고, 둘 다 불가능하면 무효.  
   - 색 값이 범위 끝: hue는 순환 처리하고, saturation/lightness는 범위 내 상수 규칙만 사용한다.  
   - 원본이 화면에 보이지 않거나 가림: 평정 시작 전 고정된 위치·거리 점검을 하고, 해결되지 않으면 해당 trial을 누락 처리한다.  
   - 변형 결과가 원본과 같음: 적용 후 실제 `SceneParams`와 렌더 경로를 비교해 같으면 trial 오류로 기록하고 재생성하지 않는다.  
   - 모양 경로 충돌 또는 모션 유형이 재생 묶음에 대응하지 않음: 조용히 다른 값으로 대체하지 않고 오류 로그와 함께 세션 시행을 중단한다.  
   근거: [SceneParams.cs:110](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:110), [SceneLoader.cs:652](unity/Assets/IFS/Runtime/Loading/SceneLoader.cs:652), [shape-mapping.md:29](docs/shape-mapping.md:29)

**가장 불확실한 결정 2개와 내부 시행 확인법**

1. **색 조작량**: 유채색 hue 0.25 회전과 무채색 saturation 0.6이 과도하거나 약하지 않은지, 내부 시행에서 원본과 변형을 블라인드 순서로 비교해 ‘차이가 보이는지’와 밝기 인상이 유지되는지 기록한다.
2. **형태 대체 순환**: 네 형상 간 지각 차이가 크게 다를 수 있다. 팀원이 순서를 모른 채 각 쌍의 차이를 간단히 평정하고, 특정 전이가 거의 같거나 지나치게 두드러지는지 확인해 해당 전이 결과를 해석상 제한으로 기록한다.
