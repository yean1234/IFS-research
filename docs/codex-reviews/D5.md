1. **결정 — 후보는 Unity 런타임에서 생성하고, 후보 데이터는 원본 spec과 정렬된 override 목록으로 표현한다.**

   **이유:** Unity의 `SceneParams`·`FormRenderPlan`·형상별 렌더러를 그대로 써야 웹 미리보기와 헤드셋 렌더가 같은 규칙을 공유합니다. Python은 확정 텍스트를 spec으로 매핑하고 후보 요청을 전달하며, 후보 계산과 렌더링은 Unity가 맡습니다.

   **구체 값·방법:** 챗봇 웹은 spec JSON과 세션 ID를 Unity WebGL에 전달하고, Unity는 `{candidateId, order, overrides, origins}` 네 후보를 반환합니다. 웹은 WebGL을 우선 표시하고, 불가 시 같은 Unity 빌드의 캡처 이미지를 씁니다. 선택·조절 후 Unity가 원본 spec에 최종 값을 적용해 `finalScene.json`을 만들고, 헤드셋 러너는 그 spec만 읽습니다. 후보 ID는 `SHA-256(canonical spec + generatorVersion + candidate index)`로 고정하고, 합성 확정 텍스트 fixture마다 spec·후보 JSON 해시를 함께 고정합니다.

   **근거 파일:** [prototype-v4-build.md](docs/prompts/prototype-v4-build.md:44) G7–G12, D3–D5·D8–D9(112–118행); [SceneParams.cs](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:56), [FormRenderPlan.cs](unity/Assets/IFS/Runtime/Rendering/FormRenderPlan.cs:89), [SceneLoader.cs](unity/Assets/IFS/Runtime/Loading/SceneLoader.cs:225).

2. **결정 — 네 가지 출처는 spec의 `_provenance`와 분리해 세션 기록의 `attributeOrigins`에 기록하고, 최종 결과는 SceneSpec v2.2로 저장한다.**

   **이유:** `_provenance`는 확정 텍스트의 근거이므로 후보 선택·기본값을 거기에 넣으면 참여자가 말한 것처럼 보입니다. 값이 null이면 `_provenance`가 없어야 한다는 규칙은 유지하고, 비어 있던 슬롯이 최종 렌더 값으로 채워질 때는 별도 출처 필드가 있어야 검증할 수 있습니다.

   **구체 값·방법:** `attributeOrigins[path] = {kind: said|chosen|edited|default, candidateId?, initialValue, finalValue}`로 기록합니다. `said`만 기존 `_provenance`를 보존하고, 나머지는 텍스트 근거를 만들지 않습니다. 스키마에 `attributeOrigins`와 `specVersion: 2.2.0`을 추가하고, 유효성 검사는 “값이 있으면 provenance 또는 origin이 있어야 함”으로 확장합니다. 원본 v2.1 spec은 덮어쓰지 않습니다. v0 출력 해시는 그대로 두고, 기존 평가 fixture는 v2.1 호환 검사와 별도로 v2.2 변환·출처 검사를 추가합니다.

   **근거 파일:** [scene-spec.v2.1.json](shared/schemas/scene-spec.v2.1.json:329), [scene_spec.py](chatbot/ifs_chatbot/scene_spec.py:90), [SceneSpecJson.cs](unity/Assets/IFS/Runtime/SceneSpec/SceneSpecJson.cs:68), [SceneParams.cs](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:68).

3. **결정 — 후보는 비어 있는 슬롯 하나씩만 벌리고, 형태 → 색 → 크기 → 질감 순으로 우선한다.**

   **이유:** 한 후보에서 한 자리만 바꾸면 선택 차이가 어떤 미지정 속성에서 왔는지 해석하기 쉽습니다. 움직임·투명도·밝기는 실제 표시 효과와 형상 밀도가 얽힐 수 있어, 첫 버전 후보 축에서는 뒤로 둡니다.

   **구체 값·방법:** 고정 후보값 표를 버전 관리합니다. 예를 들어 형태 `blob/shell/mist/fragments`, 색 `blue/green/purple/amber`, 크기 `0.7/0.9/1.1/1.3`, 질감 `0.2/0.4/0.6/0.8`이며, 각 축에서 현재 기본값과 다른 값을 순환 배정합니다. 네 슬롯이 모두 비었으면 우선순위 상위 네 슬롯을 각각 한 번 바꾸고, 슬롯이 하나뿐이면 그 슬롯의 네 표 값을 씁니다. 낱말 해석 분기는 사전 항목에 명시된 동의 범주만 허용합니다(예: “껍질”→shell/얇은 막); “빛”은 밝기와 형태를 동시에 바꾸지 않고, 별도 사전 분기가 등록된 경우에만 처리합니다. 비어 있는 슬롯이 없으면 네 후보는 같은 렌더 결과로 내고 `no_distinguishing_slot`을 남깁니다. “느낌만” 말해 속성 슬롯이 전부 비면 중립 기본값 후보를 만들고 모두 `default`로 표기합니다. 후보 순서는 우선순위·표 값 순으로 고정하며, 노출 순서와 순서별 후보 ID를 기록합니다.

   **근거 파일:** [prototype-v4-build.md](docs/prompts/prototype-v4-build.md:46) G9, D3(112행), 후보 수(135행); [scene_params.v1.json](shared/lexicon/scene_params.v1.json:261).

4. **결정 — 묶음 기본 형상은 `form.base` 별도 필드로 추가하고 `form.type`은 기존 네 값의 의미를 유지한다.**

   **이유:** `form.type`은 blob/mist/shell/fragments 렌더 경로를 선택하므로 그릇·선·천 같은 기본 형상을 여기에 넣으면 기존 렌더러 의미와 소유감 변형 규칙이 섞입니다. `_unmapped`는 미해석 원문 기록이지 렌더 값이 아니므로 기본 형상 식별 필드로 쓰지 않습니다.

   **구체 값·방법:** v2.2의 `form.base`에 사전 키(예: `container`, `line`, `sheet`)를 둡니다. `ShapeMapping`이 키를 프리팹/메시로 해석하고, `FormRenderPlan`이 기존 형태 렌더 경로와 별도 base 렌더러를 선택합니다. X22 움직임 변형은 base별 가시성을 표로 정의하고, X23 형태 변형은 새 base를 임의로 blob/mist로 치환하지 않으며 호환 변형만 등록합니다. 이행은 schema·Python lexicon → Unity ShapeMapping/plan/renderer → 변형 규칙 → 합성 fixture 순입니다.

   **근거 파일:** [ShapeMapping.cs](unity/Assets/IFS/Runtime/SceneSpec/ShapeMapping.cs:79), [FormRenderPlan.cs](unity/Assets/IFS/Runtime/Rendering/FormRenderPlan.cs:89), [OwnershipVariantGenerator.cs](unity/Assets/IFS/Runtime/Ownership/OwnershipVariantGenerator.cs:326), [prototype-v4-build.md](docs/prompts/prototype-v4-build.md:115).

5. **결정 — 조절은 각 항목을 SceneParams 슬롯에 직접 연결하고, 모든 입력을 렌더 변화 검증을 통과한 뒤 저장한다.**

   **이유:** 현재 `SetNumber`·`SetCategory`는 허용 키와 범위를 제한하지만, 기록과 화면 반영을 보장하지는 않습니다. 특히 motion은 형상에 따라 보이지 않을 수 있으므로 입력 성공만으로 반영됐다고 처리하면 안 됩니다.

   **구체 값·방법:** 형태→`form.type`/`form.base`, 색→`material.color`, 밝기→`material.brightness`, 투명도→`material.opacity`, 크기→`layout.size`, 질감→`material.roughness`(0–1), 움직임→`motion.type`(still/floating). 수치는 0–1, 0.05 간격, 범주는 표에 있는 값만 허용합니다. 입력 직후 `FormRenderPlan`에서 변경 전후 렌더 파라미터가 달라지는지 검사하고, 달라지지 않으면 해당 조절값을 허용하지 않습니다. UI 값별 검증 사례로 각 조작이 색·크기·실루엣·프레임 변화 중 지정된 화면 지표에 반영되는지 고정합니다. 변경마다 `events.csv`에 path, 횟수, 처음 값, 직전 값, 새 값, 반영 판정을 남기고 최종 spec에는 처음·마지막 값과 `edited` 출처를 기록합니다.

   **근거 파일:** [SceneParams.cs](unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs:101), [SceneLoader.cs](unity/Assets/IFS/Runtime/Loading/SceneLoader.cs:351), [FormRenderPlan.cs](unity/Assets/IFS/Runtime/Rendering/FormRenderPlan.cs:89), [prototype-v4-build.md](docs/prompts/prototype-v4-build.md:47).

6. **결정 — “맞는 것이 없다”면 후보 1을 실행용 형상으로 넘기되, 비선택 상태를 유지하고 대표성 측정에서 별도 표기한다.**

   **이유:** 이 응답은 참여자가 후보 어느 것도 심상에 맞지 않는다고 한 기록이지, 특정 후보를 골랐다는 근거가 아닙니다. 다음 단계 진행에 쓸 형상과 참여자의 선택·평정을 분리해 저장해야 합니다.

   **구체 값·방법:** `selection = none`, `operationalCandidateId = 후보 1`, `selectedCandidateId = null`로 기록하고 후보 1을 사전 측정·러너에 전달합니다. 모습 일치·대표성 응답은 수집하되 `none_selected=true`를 붙여 선택자 분석과 분리하고, 대표성 하한 점검의 분모에는 선택 결과와 함께 별도 보고합니다.

   **근거 파일:** [prototype-v4-build.md](docs/prompts/prototype-v4-build.md:31), G13(50행), 기록 단계(36행).

### 가장 불확실한 결정

- **조절이 실제 화면에서 항상 구별되는지:** Unity 렌더러별로 조절 입력을 극단값·중간값으로 넣고 캡처 지표와 눈으로 확인합니다.
- **WebGL과 데스크톱의 동등성:** 고정 spec을 양쪽에서 캡처해 평균 색·덮인 화소 수를 비교하고, 기준을 못 맞추면 문서에 정한 Unity 캡처 이미지 경로로 전환합니다.

### 12/2까지 구현 순서

1. v2.2 출처 계약과 합성 fixture를 확정합니다.
2. `form.base`의 최소 목록과 Unity 렌더 경로를 연결합니다.
3. Unity 후보 생성·결정성 기록을 구현합니다.
4. 웹 선택·“맞는 것이 없다”·조절 화면을 연결하고 최종 spec/이벤트 기록을 만듭니다.
5. WebGL 동등성과 면담부터 사전 측정까지의 전체 흐름을 확인합니다.
