너는 이 연구 저장소의 설계 자문이다. 파일을 수정하지 말고 읽기만 해라. 한국어로 답하라. 다른 설계안은 보여 주지 않는다. 네 안을 독립적으로 내라.

## 맥락
- 연구: IFS Find→Focus→Flesh out 면담 챗봇 → 확정 텍스트 → 화이트박스 규칙 매핑(SceneSpec JSON) → Unity VR 형상. 저장소 원칙은 AGENTS.md.
- 2026-11-17에 연구 질문이 바뀌었다(이전 설계는 docs/research-design.md, v0/v1 매핑 비교). 새 설계:
  1. 참여자가 심상을 자연어로 서술한다(지금 챗봇 그대로).
  2. 그 서술로 만든 원본 형상 1개와, 형태·색·크기·움직임 중 하나만 바꾼 변형본 4개를 준비한다.
  3. VR에서 5개를 무작위 순서로 하나씩, 같은 시간 동안 자유롭게 본다. 어느 것이 원본인지 알려 주지 않고, 머리 위치·방향과 거리를 기록한다.
  4. 형상마다 "내 것 같다"를 7점으로 평정하고, 마지막에 5개 중 가장 자기 것인 하나를 고른다.
- RQ1: 어떤 속성을 바꿨을 때 "내 것 같다" 평정과 선택률이 가장 크게 떨어지는가?
- RQ2: 참여자가 말한 속성을 바꿨을 때와, 말하지 않아 기본값으로 채워진 속성을 바꿨을 때 그 하락이 다른가?
- RQ3: 평정 전 행동(응시 시간, 거리, 둘러본 범위)이 원본과 변형본에서 다르고, 그 차이가 평정과 함께 움직이는가?

## 이미 알고 있는 것 (되풀이하지 말 것)
- spec에는 "기본값" 표시가 없다. 말한 값 = 슬롯 값 + `_provenance` 키. 미지정 = 슬롯 null. 기본값은 Unity가 채우고 `DefaultsUsed`에 남긴다(unity/Assets/IFS/Runtime/SceneSpec/SceneParams.cs). 기본값: form blob, HSL(0,0,0.7)(무채색), brightness 0.5, roughness 0.5, opacity 1, size 0.5, distance 0.33, motion still, speed 0.5.
- Unity 파서는 모르는 필드가 있으면 로드에 실패한다(SceneSpecJson.cs, MissingMemberHandling.Error). Python `check_principles`는 값이 있는데 provenance가 없거나 trigger가 확정 텍스트와 다르면 오류를 낸다.
- `layout.size`는 로그 척도다(0.5 = ×1, ±0.25 = ×2 / ÷2). 색은 HSL 0–1. `motion.type` 22종은 Unity에서 9묶음(Still, Sway, Tremble, Pulse, Drift, Sink, Spin, Expand, Approach)으로 재생된다(SpecMotion.cs).
- 형태는 두 경로다: `form.type`(blob/mist/shell/fragments, 프리팹 없이 절차 모형)과 모양 낱말(`_unmapped`의 category shape → Sphere/Cube/FlatCylinder/Cone 프리팹, docs/shape-mapping.md).
- 변형본 생성에는 LLM·난수 모델을 쓰지 않는다. 같은 입력(원본 spec, 참여자/세션 ID, 설정)은 언제나 같은 변형본을 내야 한다.
- 속성별 변화 크기가 지각적으로 같지 않으면 RQ1 결과가 조작 크기의 산물이 된다는 위험은 이미 안다. 이 위험을 지적만 하지 말고 구체적 대처를 내라.

## 설계해 달라는 것
변형본 4개(형태·색·크기·움직임)를 만드는 규칙. 다음 각각에 대해 하나의 안을 정하고 이유를 2–3문장으로 적어라. 대안을 나열만 하지 말 것.
1. **표현과 위치**: 변형본을 어디서(Python / Unity) 무엇으로(변형된 spec 파일 / 원본 spec + 덮어쓰기 목록 / 해석된 SceneParams) 만들고 저장할지. provenance 규칙과 Unity 파서 제약, "spec에는 말한 것만 적는다"는 원칙을 깨지 않아야 한다.
2. **크기**: 방향(키울지 줄일지)과 크기(몇 배). 방향을 어떻게 결정론적으로 정하고 참여자 간에 균형을 맞출지.
3. **색**: 유채색일 때와 무채색(기본값 포함)일 때 각각 무엇을 얼마나 바꿀지. brightness 슬롯과의 관계.
4. **움직임**: 종류를 바꿀지 속도를 바꿀지. 원본이 still(기본값 포함)일 때와 움직임이 있을 때 각각.
5. **형태**: 무엇에서 무엇으로 바꿀지(form.type 4종과 모양 모형 4종 사이). 원본이 기본 blob일 때, 모양 모형일 때, mist/shell/fragments일 때.
6. **말한 속성 / 기본값 속성 표시(RQ2)**: 변형본마다 "바꾼 속성이 말한 것인지 기본값인지"를 어떻게 정하고 기록할지. 색처럼 슬롯이 여럿(color, brightness, saturation)이거나 형태처럼 경로가 둘인 경우의 판정 규칙.
7. **변화 크기 맞추기**: 속성 간 변화 크기를 맞추거나, 못 맞추면 분석에서 다루는 방법. 12/2 투고 일정(약 2주)과 참여자 없이 연구팀 내부 시행만 가능할 수 있다는 조건에서 실행 가능한 것.
8. **빠뜨리기 쉬운 경계 사례** 최대 5개와 처리 규칙(예: 값이 범위 끝에 있음, 원본이 화면에 보이지 않음, 변형 결과가 원본과 같아짐).

## 출력 형식
- 위 1–8 번호 그대로. 각 항목: 결정 한 줄 → 이유 → 구체 값(숫자·열거값) → 근거 파일:줄(있으면).
- 마지막에 "가장 불확실한 결정" 2개와 그것을 내부 시행에서 확인하는 방법.
- 전체 120줄 이내. 칭찬·요약 서론 생략.
