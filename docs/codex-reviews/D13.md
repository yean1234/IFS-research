# D13 설계 검토

## 1. 판단

**현재 연구에는 (a) 원칙 1을 그대로 두는 것이 맞습니다.** LLM을 주 경로로 쓰는 (c)는 부적합하고, (b)는 합성 대사로 오프라인 평가를 시작할 때만 검토할 수 있습니다. 지금은 물체가 실험 자극이고 결과변수가 거리이며, 예비 연구이고 IRB 심의도 없기 때문입니다. LLM이 더 많은 슬롯을 채우더라도, 그 값이 참가자가 말한 것인지 모델이 보충한 것인지가 거리 측정에 영향을 줄 수 있습니다. 참여자 확인은 오류를 고칠 기회를 주지만, 먼저 제시된 값이 판단에 끼친 영향까지 없애지는 못합니다.

따라서 **12-02 실험에서는 LLM 추출을 사용하지 않고, `experiment.toml`의 출력과 흐름을 유지**해야 합니다. 별도 오프라인 실험에서 성능과 위험을 검토한 뒤, 필요하면 기본 꺼짐인 연구용 옵션으로 좁게 열 수 있습니다. 현재 뼈대는 LLM이 질문만 만들고 물체는 사전·규칙으로 정하며, 같은 말을 같은 물체로 만드는 설계입니다(25행). 한계로 사전에 없는 낱말을 이미 기록하고 있습니다(76행). LLM 빈칸 채우기는 이 한계를 줄일 수 있지만, 결정적 매핑이라는 연구 설계의 성질을 바꾸는 선택입니다.

논문 심사자는 “모델이 채운 물체 속성이 거리 결과에 영향을 주지 않았나?”, “같은 응답에서 왜 같은 자극이 나온다고 할 수 있나?”, “인용을 붙인 것이 실제 근거를 보장하나?”라고 물을 가능성이 큽니다. 답은 현재 연구에서는 **LLM을 쓰지 않아 자극 생성에 모델 변이를 추가하지 않았다**여야 합니다. 향후 연구에서 허용하더라도, 모델 출력은 참가자 발화의 기계적 판독 결과로 보장된다고 주장하지 말고, 출처가 분리된 제안값이며 확인 전에는 장면에 적용하지 않는다고 밝혀야 합니다.

제시된 선행 연구는 서지를 기억으로 보완하지 않았습니다. 확인 가능한 범위에서 LLMER는 LLM 생성 JSON으로 XR 환경을 만드는 연구이고, HOG-Layout은 텍스트 기반 계층형 3D 장면 생성·편집 연구이며, PARSE는 스키마 기반 엔터티 추출 연구입니다. 이들이 **이 연구의 발화 속성을 근거 인용으로 제한하거나, 거리 결과변수에 안전하다는 근거인지는 확인되지 않았습니다**. 응용 가능성과 이 연구에서의 타당성은 별도로 평가해야 합니다. ([LLMER](https://pure.psu.edu/en/publications/llmer-crafting-interactive-extended-reality-worlds-with-json-data/), [HOG-Layout](https://openaccess.thecvf.com/content/CVPR2026/papers/Jiang_HOG-Layout_Hierarchical_3D_Scene_Generation_Optimization_and_Editing_via_Vision-Language_CVPR_2026_paper.pdf), [PARSE](https://aclanthology.org/2025.emnlp-industry.184/))

## 2. 과한 해석을 막는 장치

인용 문자열 검사는 “그 글자가 원문에 있다”만 보장합니다. 「무거워요」를 그대로 인용해도 색을 짙게 채우면 과한 해석입니다. 따라서 슬롯별로 **값을 직접 말한 표현**을 사전에 정의하고, 그 표현과 값의 관계가 허용된 경우에만 후보로 받아야 합니다.

| 슬롯 | 허용할 근거의 기준 예시 | 허용하지 않을 것 |
| --- | --- | --- |
| 형태·물체 종류 | 해당 형태나 물체를 직접 가리키는 명사·표현 | 감정·비유에서 모델이 유추한 형상 |
| 색·밝기·질감 | 색·밝기·질감을 직접 서술한 표현 | 「무거워요」→짙은 색, 「차가워요」→금속 |
| 크기 | 크기 또는 비교 대상을 포함한 직접 표현 | 강조어·감정 강도에서 크기를 추정 |
| 위치·거리 | 위치·방향·거리의 직접 표현 | 등장 순서나 문맥으로 위치 추정 |
| 비율·투명도 등 | 각 슬롯에 허용된 직접 표현과 명시적 대상 | 다른 슬롯의 형용사를 옮겨 채우기 |

최소 인용 단위는 **값을 뒷받침하는 가장 짧은 연속 구간이되, 부정·가정·과거·타인의 발화·비유 여부와 서술 대상까지 판정할 수 있을 만큼의 문맥을 포함**해야 합니다. 고립된 형용사만 인용하게 하면 「진하지 않으면 좋겠다고 생각했어요」에서 부정·가정이 사라집니다. `charSpan`은 확정 원문에서 반개구간(`[start, end)`)으로 정하고 인용문이 그 구간과 정확히 일치하는지 검사해야 합니다.

한 인용이 여러 슬롯을 채우는 것은 **각 슬롯을 별도로 직접 말한 경우에만** 허용합니다. 「빨갛고 거칠어요」는 색과 질감 각각의 근거 구간을 가질 수 있지만, 「무거워요」 하나를 크기·색·질감에 두루 쓰면 안 됩니다. 기계는 범위·일치·슬롯 허용 목록·enum·부정/시제/대상 규칙의 일부를 검사할 수 있습니다. 인용의 의미가 실제로 슬롯 값을 함의하는지, 비유가 사실 진술인지, 규칙이 포착하지 못한 문맥인지는 기계 검사만으로 보장하기 어렵습니다. 이 부분은 사람 판정이 필요합니다.

## 3. 출력과 검증기

LLM 출력은 완전한 IFSSceneSpec이 아니라, **매퍼가 비워 둔 허용 슬롯에 대한 후보 목록**으로 제한합니다. 예를 들면 다음 정도입니다.

```json
{
  "proposals": [{
    "slot": "material.roughness",
    "value": 0.8,
    "charSpan": [12, 15],
    "quote": "거칠어요",
    "evidenceType": "direct_attribute"
  }]
}
```

`evidenceType`은 `direct_noun`, `direct_attribute`, `direct_measure`, `direct_spatial`처럼 사전에 정한 값만 허용합니다. 자유서술 근거 유형은 받지 않습니다. JSON 스키마와 제약 디코딩은 형식 오류를 줄이는 데 쓰되, 근거의 의미를 증명한다고 간주하면 안 됩니다. 검증 실패는 **재시도 없이 해당 후보를 버리고 슬롯을 빈 상태로 둡니다**. 재시도는 출력 차이를 늘리고, 실패한 후보를 사후적으로 구제하는 별도 경로를 만듭니다.

우선순위는 **기존 매퍼 값 > LLM 후보**입니다. 이미 값이 있거나 매퍼가 부정·비유·대상 불일치 등으로 막은 슬롯에는 LLM이 덮어쓰지 못하게 해야 합니다. `_unmatched`에 낱말이 있다는 사실도 그 낱말이 슬롯 값이라는 뜻은 아닙니다. 따라서 빈 슬롯이면서 별도의 규칙 검사를 통과한 후보만 참여자 확인 대상으로 보냅니다.

## 4. 재현과 기록

`temperature=0`, seed, 모델 digest를 기록해도 “같은 말이면 같은 물체”를 모든 환경에서 보장할 수는 없습니다. Ollama 및 모델 런타임, 하드웨어, 양자화, 템플릿·시스템 프롬프트, 토크나이저 등이 달라질 수 있고, seed가 그 차이를 없애지는 않습니다. 같은 PC·같은 고정 환경에서도 반복 일치율을 실측해야 합니다. 다른 PC 간에는 **같은 출력 보장** 대신 버전·해시·설정이 같은 조건에서의 재생성 시도와 결과 비교가 현실적인 보장입니다. 원본 발화 캐시는 개인 응답을 담으므로 저장한다면 합성 자료 평가에 한정하고, 참여자 자료는 git에 올리지 않아야 합니다.

기록할 항목은 모델 파일 digest, Ollama/런타임 버전, 프롬프트·스키마·검증기 digest, seed와 생성 설정, 확정 텍스트 해시, 매퍼·사전 버전, 원시 후보와 폐기 사유, 참여자 승인·수정 결과입니다. 실제 값의 출처는 `llm`으로 따로 유지하고, 참여자가 승인한 사실은 별도 확인 기록으로 남기는 편이 낫습니다. 기존 provenance 필드를 확장한다면 허용되는 출처와 증거 구조를 스키마에 명시하고 버전을 올려야 합니다. 실험 스펙은 바꾸지 않도록, 오프라인 제안·확인 기록을 기존 실험 스펙과 분리된 sidecar로 두는 방안이 안전합니다.

## 5. 참여자 화면

현재 연구에서는 LLM 제안값을 화면에 띄우지 않습니다. 오프라인 평가 뒤 별도 연구에 도입한다면, 후보 화면에서 기본 선택값처럼 먼저 보이지 않게 해야 합니다. 참가자가 매퍼 기반 화면을 먼저 보고 응답한 다음, 독립된 확인 단계에서 제안값·원문 인용·“사용/수정/비워 두기”를 제시하는 방식이 암시 효과를 줄이는 데 도움이 됩니다. 다만 그 단계도 암시를 없애지는 못하므로, **거리 측정에 쓸 실험에서는 승인된 LLM 값이 자극에 반영되지 않도록** 먼저 검토해야 합니다.

문구는 선택을 유도하지 않는 초안으로 제한합니다. 예: “다음 값은 말씀에서 자동으로 찾은 초안입니다. 사용하거나, 고치거나, 비워 둘 수 있습니다.” `shared/protocol/`에 고정 문구로 넣는다면 원칙 7에 따라 `status`, 출처, 프로토콜 버전을 함께 기록해야 합니다. 치료·진단 표현은 쓰지 않습니다.

## 6. 평가 설계와 사전 기준

켜기 전 평가는 `chatbot/scenarios/`와 `docs/validation/`의 **합성 대사만** 사용합니다. 기존 매퍼가 놓친 표현, 직접 속성 언급, 부정·가정·과거, 타인 발화, 비유, 중의성, 상충 표현, 무관한 unmatched 낱말을 포함하고, 표현 틀은 학습·조정 세트와 held-out 세트로 분리합니다. 정답은 각 슬롯별로 “직접 말함 / 말하지 않음 / 판정 불가”를 사람이 사전 작성합니다.

근거 없는 값과 과한 해석 비율은 두 명이 모델 출처와 매퍼 결과를 모른 채 독립 판정하고, 불일치는 제3자가 조정합니다. 지표는 근거 없는 제안 비율, 과한 해석 비율, 빈 슬롯 채움률, 매퍼와의 일치율, 동일 조건 반복 실행 일치율입니다. “빈칸 채움”은 정답이 직접 말함인 슬롯 중 유효 후보가 생긴 비율로 정의합니다.

사전 통과 기준 예시는 **held-out 200개 이상 대사·400개 이상 슬롯 후보**, 근거 없는 값 0건, 과한 해석률 1% 이하이며 95% 신뢰구간 상한 2% 이하, 기존 매퍼 값과의 충돌 0건, 채움률 10% 이상, 동일 고정 환경 반복 일치율 100%입니다. 표본 수가 이 기준의 신뢰구간을 평가하기 부족하면 통과로 보지 않습니다. 근거 없는 값 1건이라도 나오거나, 안전 규칙 위반·기존 매퍼 덮어쓰기·반복 불일치가 발견되면 즉시 중단하고 원인을 수정한 뒤 새 held-out 자료로 다시 평가합니다. 이 기준은 자동 허가가 아니라 다음 단계 검토의 문턱입니다.

## 7. 문서 문장 초안

이번 판단은 원칙을 그대로 두는 것이므로 지금 원칙 1이나 뼈대 25행을 바꾸지 않는 안을 권합니다. 향후 오프라인 평가를 통과해 제한적 실험 경로를 승인한다면, 예외를 명확히 닫아 둔 문장은 다음과 같습니다.

- **AGENTS.md 원칙 1:** “LLM은 면담 질문 생성에만 쓴다. 다만 별도 승인된 오프라인 평가에서, 기본 꺼짐인 연구용 경로가 매퍼의 빈 슬롯에 출처 `llm`의 후보를 제안할 수 있다. 인용 범위·규칙·허용 슬롯 검사를 통과하고 참여자가 확인하기 전에는 스펙 값이나 장면에 반영하지 않는다. 확정 텍스트만으로 추출을 재현할 수 있다고 주장하지 않으며 모델·런타임·프롬프트·검증기 digest와 텍스트 해시를 기록한다.”
- **AGENTS.md 원칙 2:** “LLM의 인용문이 원문에 있어도 슬롯 값의 근거가 되는 것은 아니다. 각 슬롯의 직접 진술 기준을 정하고, 그 기준을 기계 검사와 사람 평가로 확인한다. 사용자가 확인하지 않은 후보는 빈 값으로 둔다.”
- **뼈대 25행:** “기본 경로에서 물체는 사전과 규칙이 만들고 같은 확정 텍스트는 같은 결과를 낸다. 별도 평가 경로의 LLM은 빈 슬롯에 출처가 표시된 후보만 제안하며, 확인 전에는 자극을 바꾸지 않는다. 이 경로의 결과는 결정적 매핑으로 간주하지 않는다.”

이 문장들도 현재 연구에서의 LLM 사용을 허용하는 근거로 삼아서는 안 됩니다. 적용 전에는 설계 결정 기록과 프로토콜 변경 범위를 별도로 검토해야 합니다.

## 8. 가장 약한 곳 세 가지

1. **인용은 의미 검증이 아닙니다.** 명시적 표현 목록과 규칙을 늘려도 한국어의 맥락·비유·대상 해석을 완전히 포착하지 못합니다.
2. **확인 화면도 중립적이지 않습니다.** 참가자가 제안을 거부해도 먼저 본 값이 이후 판단에 남을 수 있어, 거리 결과변수의 오염을 배제하기 어렵습니다.
3. **재현 기록은 모델의 결정성을 만들지 않습니다.** digest와 seed는 조건을 추적하게 하지만, PC·런타임이 달라졌을 때 같은 물체가 나오는 것을 보증하지 않습니다.
